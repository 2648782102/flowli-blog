# Visual Brief — flowli 的个人博客

日期：2026-11-11（Asia/Shanghai）

## 背景

当前博客基于 Astro/Twilight，已经具备内容管理、GitHub Pages 自动部署、RSS/Atom、搜索、归档、标签、分类、作品、技能、时间线等能力。视觉方向曾多次尝试「藏蓝 + 液态玻璃」，但缺少参考锚点、唯一设计契约和截图验收，导致样式源叠加、玻璃材质覆盖过多、信息层级被削弱。

本次只建立视觉设计前期的可评审产物，不修改 `src/`，不改变线上样式，不提交代码。

## 页面任务

- Audience：flowli 自己，以及对前端、工具实践、AI 开发流程和个人记录感兴趣的读者。
- One job：让读者在 10 秒内知道这是一个个人技术/生活记录站，并能顺利进入最新文章或归档。
- Core claim：这是 flowli 长期维护的公开笔记，内容比装饰更重要；技术文章要有足够好的阅读体验。
- Proof：真实文章、真实日期、真实分类/标签、GitHub 仓库、持续更新的归档与订阅入口。

## 当前基线结论

基线截图位于 `design/screenshots/current/`：

- `home-desktop.png` / `home-mobile.png`：当前首页。
- `post-desktop.png`：当前文章阅读页。
- `archive-desktop.png`：当前归档页。

从 `home-desktop.png` 可直接看到：

1. 顶部导航、Hero、左右侧栏、文章卡片、公告、音乐按钮都使用相近的透明圆角表面，视觉层级没有主次。
2. 风景 banner 占据大面积视觉注意力，随后 Hero 玻璃板再覆盖在 banner 上，形成两次抢焦点。
3. 文章卡片与侧栏卡片形状、阴影、留白接近，正文阅读区域不够安静。
4. 元数据、分类、标签、公告和音乐控件同时出现，首页像仪表盘而不是博客。
5. 当前内容里出现测试标题与占位感文案，设计评审必须使用真实内容或明确标注为测试数据。

## 设计目标

- 把「阅读」放到第一层级：文章标题、摘要、正文排版优先于材质、壁纸和装饰。
- 保留个人气质，但不让 AI 默认审美主导：少渐变、少发光、少同款卡片、少玻璃覆盖。
- 主色仍可为藏蓝，但只作为文字、选中态、链接和少量强调；背景以稳定的纸面/冰蓝中性色为主。
- 液态玻璃只能作为功能层材质，优先限制在导航、临时菜单、搜索面板等需要「浮在内容之上」的组件；正文、文章卡片、侧栏不使用实时模糊。
- 建立唯一 token source，后续重构必须先合并/删除重复 CSS 变量，再加新效果。
- 所有方案必须通过桌面、移动、Tab 选中态、切换抖动、focus、reduced motion 与对比度检查。

## 非目标

- 不复制任何参考站的品牌、文案、图片、专有布局或交互。
- 不把整个 Astro 项目改成 React/Next.js；v0/Figma 输出只作为规格与视觉目标。
- 不直接删除内容功能；本阶段只决定视觉和信息层级。
- 不在本阶段修改 `src/`、`twilight.config.yaml`、部署配置或提交/推送。

## 内容约束

- 使用真实中文文章：`测试123` 与 `今天的心情是寂寞的` 当前是 CMS 测试内容，后续视觉稿中应替换为真实文章或标注为 sample。
- 正文行长控制在 50–75 个中文/英文混排字符的视觉等价范围，代码块可横向滚动。
- 首页最多暴露一个首要动作：进入最新文章 / 浏览全部文章；其余入口降级到导航或页脚。
- 禁用占位卡片、假数据、假评价、无意义的 01/02/03 序号。

## 验收清单

来自 `taste-checklist.md` 与本项目历史问题，后续每轮截图必须检查：

- [ ] 10 秒测试：能说出这是谁、写什么、下一步读哪里。
- [ ] 同一页面不超过两种字体角色，字号阶梯有明确跳跃。
- [ ] 正文、文章卡片、侧栏不使用玻璃模糊；玻璃只出现在功能浮层。
- [ ] 桌面 1440×900 与移动 390×844 均无横向滚动。
- [ ] 顶部 Tab 在所有页面都有稳定选中态，切换不抖动。
- [ ] 首页与其他页之间切换时，导航高度、主内容起点和滚动位置没有跳变。
- [ ] 所有交互元素有 hover / focus / active / visited 状态，focus 清晰可见。
- [ ] `prefers-reduced-motion` 下关闭非必要动画与玻璃位移。
- [ ] 文本对比度满足 WCAG AA；深色模式是独立设计，不是简单反色。
- [ ] 每轮并排比较当前基线、选中方向、参考图；评审通过后才改代码。

## 工作流约束

1. 人类选择方向 A 或 B。
2. AI 只按选定方向生成 `DESIGN.md` 的最终 token 与组件契约。
3. 实现按模块拆开：token → 栅格 → 导航/Tab → 文章卡片 → 正文 → 侧栏/浮层 → 深色模式/移动端。
4. 每轮用 `design/capture-screenshots.mjs` 重新截图，写入 `design/review.md`。
5. 只有截图检查、`pnpm check`、`pnpm build` 都通过，且人类批准后，才进入提交/推送。
